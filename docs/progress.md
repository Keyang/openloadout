## Decisions from Keyang (2026-11-18)

- Game types: chosen by research on the top 100 2D games (task W1-R). Result: **platformer** (side view, fantasy), **turn-based RPG** (top-down overworld, side-view battles, fantasy), **roguelike action** (top-down, sci-fi). Bundle ids: `kit-platformer-fantasy`, `kit-rpg-fantasy`, `kit-roguelite-scifi`.
- Bundle size: 40–50 sprites, 20 sounds, 2 music tracks each.
- "Play" is a playground for trying bag assets, not fixed template games.
- Export: the user chooses zip or Unity package; Unity is "coming later" and not built in this loop.
- Git: local commits allowed, no pushing. Dependencies and one embedding-model download allowed.
- Search defaults accepted: SQLite file, English, model served from the site, background download. After measurement and review (2026-11-18 17:00) the orchestrator made search by meaning an opt-in switch, off by default: it missed the pass mark and costs 38.5 MB. Keyang can reverse this.
- Out of this loop: MCP route, studio, physics, 3D, hosting, accounts.
- In this loop: parts, the automatic quality bar with an independent reviewer.
- No ceiling on time or spend. The project is called Loadout.
- **17:50, two layers.** The framework (foundation) and the assets synthesized on demand from it. When making an asset shows the framework lacks something, add it to the framework, not to the asset file. Everything in the framework must be reachable as `window.*` functions so an MCP server can use them as tools. Start simple; the framework grows as assets get more varied and complex. Recorded as Contract 11 in `docs/architecture.md`. The orchestrator's reading: the `window` functions and their machine-readable description are now in this loop; the MCP server itself is still later.
- **18:40, styles.** After `docs/sprite-styles.md` and `docs/sprite-data.md` (written in another session): one asset may offer several styles to synthesize and export; styles that are not possible or make no sense for an asset are omitted; not a priority now, but the framework must support different rendering and export pipelines. Recorded as Contract 12 (designed; field names reserved). The orchestrator's reading: build the seam (a style registry with today's pixel pipeline as its one entry, style recorded as data, a per-style exporter) once the run-time asset work lands, prove it with a test-only second style, and give no real asset a second style in this loop.

Recorded as Contract 13 in `docs/architecture.md` with the reading Keyang then confirmed (the rig is code; a sprite on a rig is data only) and three open questions, R2 to R4; nothing is built or queued.
